# Familiar · 灵伴：首版范围与参考项目调研 v0.1

日期：2026-09-17。状态：首版范围基线；已进入本地开发预览，实际实现与验证边界见文档 04、05。

## 1. 本轮需求与结论

用户已明确：

- 先做有陪伴感的桌面宠物，首版接入文字 LLM。
- 桌面控制器负责配置，宠物独立运行，不依赖控制器保持打开。
- 后续再发展 Agent 能力，当前不扩展语音、视觉、工具和自动化。
- 首版可以使用 2D，但架构不能限制以后使用 3D。
- 不需要聊天页面；采用宠物头顶气泡和按需出现的文字输入条，推理内容不展示。

建议首版定位为：**Windows 上独立常驻、可配置、可换角色、可以持续文字聊天的桌面伙伴。**

首版可交付体验：启动宠物 → 本地待机与互动 → 打开控制器配置模型 → 从宠物旁发起聊天 → 关闭控制器后继续聊天 → 重启后恢复角色、位置、设置与近期对话。

本文写于应用实现之前，补充首版范围和开工顺序，不修改原有长期理念。2026-09-17 依照用户修正，将聊天面板方案替换为头顶气泡与临时输入条。

原总体设计第 36、37、47 节将无 LLM 宠物和 LLM 聊天分为先后阶段。本轮需求将它们纳入同一个首版交付：内部仍先跑通桌宠，再接 LLM。保留 Plugin First、Thin Kernel、平台抽象及生命周期原则，不要求首版提前交付完整社区平台。

### 2.1 关于独立运行的实际证据

[OpenPets 桌面文档](https://github.com/OpenPetsHQ/openpets/blob/main/docs/desktop.md)明确由 Electron 主进程统一拥有宠物窗口和控制中心，控制中心是独立 renderer，并非另一套独立应用宿主。[OpenPet 入口文件](https://github.com/dengyie/OpenPet/blob/main/main.js)也将设置窗口、宠物窗口及各服务装配进同一个应用运行时。

因此，它们可以启发职责分离，但不能仅凭“有两个窗口”就宣称已经满足 Familiar 的两个应用独立生命周期要求。

### 2.2 内容与代码分开评估

VPet README 对代码和自带动画分别给出授权说明；Open-LLM-VTuber README 也明确 Live2D 示例素材使用独立条款；WinPet README 标注 MIT with Commons Clause。若以后实际采用代码或素材，再按具体文件和版本核对，不能把仓库许可证视为全部角色素材的统一授权。本轮没有复制第三方代码或素材。

## 3. 进程与状态归属

建议首版采用两个独立应用入口，共享一套协议和模块：

```text
Familiar Controller（按需启动，可完全退出）
  配置页面 / 模型连接测试 / 宠物运行状态
                      │
                  本地 IPC
                      │
Familiar Pet Runtime（当前用户会话中常驻）
  宿主：配置权威状态 / 生命周期 / 托盘 / 本地数据
  插件：Windows 平台 / 行为 / 角色 / 渲染 / 聊天 / Provider
  表现：宠物窗口 + 头顶气泡 + 按需出现的文字输入条
```

“两个应用入口”是生命周期边界，不承诺任务管理器中刚好两个 OS 进程；Electron 等框架本身会产生渲染、GPU 等辅助进程。

宠物运行时应是当前登录用户下的普通常驻应用。Windows Service 存在会话隔离，不适合作为首版宠物界面宿主，参见 [Microsoft Interactive Services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)。

运行语义：

- 宠物可单独启动；同一用户会话只允许一个 Runtime 实例。
- 控制器可单独打开；未连接 Runtime 时显示“宠物未运行”和启动入口。
- 首版配置编辑在连接 Runtime 后进行，不另建离线配置写入路径。
- 关闭或强制结束控制器，不影响宠物动画、会话及正在进行的模型请求。
- 气泡与输入条由 Runtime 持有；聊天不需要打开控制器，不渲染聊天记录页面。
- 隐藏宠物、暂停互动、退出宠物是不同操作；明确退出时取消请求、清理窗口和托盘。
- 控制器断开后重连，重新获取完整状态；Runtime 退出后，控制器显示离线，不能继续假报保存成功。
- 开机启动默认关闭，启用后只启动 Runtime。
- 首版无需独立守护进程或自动重启服务；崩溃恢复先做到重启不丢已提交设置和完整消息。

### 3.1 设置如何真正生效

Runtime 是唯一持久化写入者；控制器通过命令修改，不同时直接改同一个配置文件。

流程：读取当前版本 → 提交修改 → Runtime 校验 → 准备并应用 → 原子保存 → 返回已生效版本并广播状态。

需要分清三种结果：`applied`（已生效）、`requiresRestart`（已保存待重启）、`rejected`（拒绝且维持原状态）。应用或保存失败时回滚可回滚的变更；无法回滚的系统设置需报告实际状态，不能统一显示成功。

| 设置 | 建议生效时点 |
| --- | --- |
| 大小、置顶、可见性、安静模式 | 立即生效并回传实际值 |
| 角色替换 | 新资源验证并准备成功后切换；失败保留旧角色 |
| Provider、模型、人格 | 下一轮对话；当前轮使用启动时的配置快照 |
| 登录自启动 | 系统调用成功后回传状态；失败显示具体原因 |

IPC 最小契约建议包含协议版本、请求 ID、配置版本和结构化错误。命令先仅保留状态读取、配置应用、模型测试、显示/隐藏、重置位置、退出。重试不能产生重复应用；版本冲突应刷新后重试。

Windows 本地通信可选命名管道，并限制当前用户/会话访问；若选择 .NET，可参考 [PipeOptions.CurrentUserOnly](https://learn.microsoft.com/en-us/dotnet/api/system.io.pipes.pipeoptions)。传输实现随技术栈验证，但首版不开放远程控制。

| 部分 | 必须交付 |

| 控制器 | 宠物状态、外观/行为设置、LLM 配置、连接测试、数据清理入口 |
| LLM | 一个可替换的兼容接口 Provider；支持填写 Base URL、模型 ID、可选 Key |

首版一个宠物实例、一个默认角色包、一种渲染器、一个激活模型即可。以第二个极简测试角色验证“换角色无需改 Core”，不要求同时制作第二套正式美术。

本地模型通过用户已有的兼容服务接入，不把下载模型和内置推理引擎纳入首版。兼容协议也需要针对实际目标服务验证流式、错误与取消，不能承诺所有同名兼容接口都完全一致。

首版明确后置：语音、屏幕/摄像头、工具调用、MCP、任务规划、多 Agent、长期语义记忆、向量库、主动 LLM 轮询、养成经济、多宠物、账号同步、插件市场、Android。

## 5. 陪伴感不依赖持续模型调用

本地行为插件处理待机节奏、眨眼/呼吸、点击反馈、拖动和睡眠。LLM 只在用户发送文字时调用，模型未配置或不可用时仍有正常桌宠。

首版先用对话事件映射表现：开始生成 → 思考；收到文字 → 展示；完成 → 恢复待机；失败 → 短暂提示。不要为情绪识别额外调用一次模型，也不要强制每个 Provider 输出复杂 JSON 才能聊天。

人格采用独立配置，包含名字、性格、称呼和表达习惯；与近期聊天记录分开。聊天记录用于跨重启延续上下文，不等同于长期记忆系统。

聊天模块需有：

- 单轮请求 ID；一只宠物同一时刻一轮生成，用户可停止再发送。
- 上下文预算与最近消息截取；历史可以保存更多，但不无限发送给模型。
- 流式文本不阻塞动画；失败/取消保存明确状态，不把残缺回复当完整结果。
- 网络超时、鉴权失败和限流可识别；重试由用户触发，避免重复计费和重复消息。
- 气泡长度和停留时间有限，长回复在可收起面板阅读。
- 提供清空当前会话与删除历史的明确语义；清空当前会话时取消旧请求，丢弃迟到结果，避免重新写回已清除内容。
- 默认不主动发送用户没有输入的桌面信息；首版不读取其他窗口内容。

## 6. 首版 2D，保持 3D 可接入

拆开四个概念：

1. **Character**：身份、人格、可用动作语义和不同表现资源。
2. **Behavior**：此刻处于什么状态、动作优先级、能否中断以及何时恢复。
3. **Renderer**：把动作意图映射为具体表现，首版是精灵帧，未来可以是 Live2D、VRM 或其他 3D。
4. **Desktop Surface**：原生窗口、输入命中、屏幕位置、可用区域、缩放与显示器变化。

上层协议只传 `idle`、`sleep`、`greet`、`attention:user` 等语义与请求 ID；帧序号、骨骼、摄像机、具体动画 clip 留在对应渲染器。

角色清单的表现资源应按表现类型组织，例如 `representations.sprite`、未来的 `representations.vrm`。通用身份信息不依赖 `spritePath`、帧宽或 2D 坐标；这些字段属于 sprite 专有描述。

Renderer 声明自己能加载的格式及支持的表现能力。Character 声明已有动作与回退。渲染器对外提供加载、释放、语义动作、表现状态反馈等最小契约；具体方法签名在原型中确定，不提前冻结公开 SDK。

输入链也要隔离：窗口坐标先由具体渲染器做命中测试，再报告“点击角色”“拖动角色”等语义事件。2D 可使用透明度遮罩，3D 可用射线拾取，业务层不用知道差别。

首版可提供一个 2D 场景锚点，表示宠物位于桌面哪里；不要将角色内部世界限制成该二维坐标。未来 3D 的相机、光照、骨骼、材质与内部世界变换由 3D 渲染器拥有。

这里保证的是业务边界可复用，不承诺 3D 只需换一个文件：未来仍要实现资源加载、镜头、性能、命中测试和窗口适配，也不能保证每个 2D 角色自动获得 3D 模型。

## 7. 插件基础做到多小

首版只运行随应用发布的可信官方功能插件，以及不执行代码的角色资源包。

保留一个最小 Plugin Runtime：版本化清单、能力注册与依赖检查、生命周期、资源清理集合、配置校验、错误定位、最小权限拒绝能力。安装/卸载可先由随包目录的注册和注销实现，无需安装商店。

官方模块建议：`platform-windows`、`renderer-sprite`、`behavior-basic`、`conversation-basic`、`provider-compatible`、本地存储适配与示例角色。Kernel 不导入这些具体实现，由 Host 装配。

通过受控异常测试验证 Provider 出错、缺失动作、角色资源损坏和生命周期清理的降级。进程内异常边界无法隔离任意原生崩溃或恶意插件；不能宣称已经完成社区代码沙箱。实际开放第三方可执行插件前，再实现隔离与权限边界。

## 8. 技术路线建议与开工顺序

考虑本轮参考项目及未来不同角色渲染形式，建议优先验证 **TypeScript + Electron** 路线：Runtime 与 Controller 为两个独立应用入口，协议和领域模块共享；首版使用 2D 精灵渲染，Controller 使用常规 Web UI。

这是工程建议，不是已经验证的性能结论。AIRI 桌面包使用 Electron 且分开依赖 Live2D/Three 相关模块，见其 [package.json](https://github.com/moeru-ai/airi/blob/main/apps/stage-tamagotchi/package.json)。OpenPets 也提供了这一生态中的桌面宿主和插件组织参考。

备选为 C#/.NET + WPF，适合 Windows 优先的原生桌面路线。WPF 本身只运行于 Windows，参见 [官方概览](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)；若选它，未来跨端共享协议和领域语义即可，不强求复用界面。

最终选型先通过窗口原型验证。尤其 [Electron 官方文档](https://www.electronjs.org/docs/latest/tutorial/custom-window-styles)指出透明区域不会自动鼠标穿透，因此透明、命中和穿透必须作为独立验证项。不要仅凭截图里的透明效果就认定桌面交互合格。

| 顺序 | 交付物 | 通过标准 |
| --- | --- | --- |
| P0 桌面与进程原型 | 可拖动的占位宠物、两个独立入口、托盘和最小 IPC | 结束控制器后宠物仍在；可单独重开控制器读取状态；窗口输入正确 |
| P1 宠物最小闭环 | 最小 Kernel、平台/渲染/行为插件、一个角色包 | 不联网可互动；替换测试角色不改 Core；停止插件清理订阅和计时器 |
| P2 配置闭环 | 控制器页面、Runtime 校验/保存/回传 | 修改立即可见；错误不污染配置；重启能恢复；断线不假报成功 |
| P3 LLM 闭环 | 可替换 Provider、人格、流式聊天和近期会话 | 控制器关闭仍可聊天；停止生成有效；网络故障不冻结宠物 |
| P4 可交付版本 | 安装/启动入口、登录自启动选项、数据清理、桌面测试记录 | 普通用户权限可运行；退出无残留任务；长期待机无明显资源增长 |

P0 的重点是验证最难返工的桌面与生命周期行为，不先铺几十个空包。每一步都保留一个可运行的软件。

## 9. 首版验收清单

- [ ] 未配置 LLM 时，宠物可以启动、待机、拖动和响应点击。
- [ ] 控制器从未打开时，Runtime 可恢复已保存配置并独立聊天。
- [ ] 关闭和强制结束控制器，分别验证宠物及正在进行的聊天不受影响。
- [ ] 重开控制器能看到 Runtime 的真实状态，不误报默认值。
- [ ] 修改设置后，显示明确的已生效/待重启/失败结果；失败保留有效配置。
- [ ] 重复启动不产生第二只意外宠物或两个并发配置写入者。
- [ ] 流式回复、停止、超时、401、429、断网和迟到响应都有明确结果。
- [ ] 切换模型或人格不会污染正在生成的轮次。
- [ ] 多显示器、负坐标、缩放 100%/150%/200%、拔掉副屏后能恢复可见位置。
- [ ] 中文输入法、拖动、透明区域命中、点击穿透和托盘恢复分别验证。
- [ ] 全屏/安静模式行为明确；默认不以主动气泡打断用户。
- [ ] 角色缺少动作能回退，损坏资源不会破坏已有有效角色。
- [ ] 角色/渲染接口无强制精灵帧字段；另一个测试适配器能消费同一动作语义。
