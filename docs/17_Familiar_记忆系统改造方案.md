# Familiar 记忆系统改造方案

日期：2026-10-11。版本：v0.1。架构决策编号：`ADR-2026-10-11-02`。

状态：**第一步（主模型维护的分层记忆）已决定并实施，验证结果见 [验收记录](05_Familiar_本地预览验收记录_v0.1.md)；第二步（向量模型）和第三步（Jev 等判断模型）是候选设计，尚未实现。** 本文中第二、三步的能力名、数据结构和阈值都不代表已有 API。

上层约束见 [开发宪法](02_Familiar_开发宪法_v0.1.md)，当前实现说明见 [记忆与 Agent 扩展](08_Familiar_记忆与Agent扩展.md)，会话压缩见 [文档 11](11_Familiar_重要日记与会话压缩.md)。

## 1. 背景与决定

v0.2 的记忆有三个问题：核心记忆只能追加，偏好改变后新旧矛盾的条目会并存；核心超过 3000 字符时由模型自动精炼，规则可能被悄悄改写；教训按时间戳一条一个文件，模型不知道有哪些教训，也就很少去读。

参考了 OpenClaw 与 Hermes Agent 的记忆设计（来自 2026-10-11 的外部调研对话，本仓库未运行或复制它们的代码）：OpenClaw 多文件分层、带来源管控，但首轮注入的上限很宽；Hermes 把常驻记忆压得很小以保住提示词缓存，写满时报错并要求模型自己合并。Familiar 取两者之长：

1. **核心记忆是路由表加硬规则，不存内容本身。** 只放用户要求必须遵守的规则和长期偏好，再加上一张“什么时候读哪个文件”的索引。项目进度、经历和资料不进核心。
2. **核心锁死上限，写满拒绝，不做有损压缩。** 规则改写后约束力会变弱，所以超限时由模型合并、删除，或把只适用于某个主题的规则移到扩展记忆。
3. **索引由程序生成。** 每个教训/扩展文件头部写一行“何时读”，程序扫描后拼成索引；不花模型调用，文件改名或删除后也不会留下失效指针。
4. **判断做成选择题接口。** 是否重复、取代哪条等判断由 `memory.judge` 能力回答固定题目，后端可替换。第一步由主模型回答，第三步换成更便宜的判断模型时不改流程。
5. **从第一步开始记录。** 判断的题目与答案、每轮注入的记忆量、每次检索与随后读取的文件都写入日志，作为第二、三步的对比基准。

## 2. 三步路线

| 步骤 | 内容 | 状态 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 第一步 | 主模型维护分层记忆：核心规则、程序索引、日记、教训、扩展记忆；`memory.judge` 主模型实现；记录日志 | 已实施（本次） | 自动化测试与烟雾测试通过；用真实模型积累至少数周日志 |
| 第二步 | 向量模型为召回和查重挑选候选，减少主模型的读取与判断量 | 候选 | 离线回放：命中率不低于第一步基线，且每轮记忆 token 下降 |
| 第三步 | Jev 等判断模型作为 `memory.judge` 的另一实现，主模型兜底 | 候选 | 离线回放：与人工修正后的答案一致率达标，中文样本实测通过 |

每一步达不到条件就停在上一步，不带着问题往下叠。

## 3. 第一步设计（已实施）

### 3.1 分层与数据

```text
home/memory/
  CORE.md              # 核心规则，随会话注入，上限 2000 字符
  IDENTITY.md SOUL.md USER.md AGENTS.md   # 身份与相处约定，原样保留
  lessons/<主题>.md     # 教训：头部“何时读”，每条“规则 — 原因”
  topics/<主题>.md      # 扩展记忆：只适用于某个项目或某类任务的约定与资料
  daily/YYYY/MM/YYYY-MM-DD.md            # 日记，只追加
  .history/            # 编辑前备份
data/
  memory-trace-YYYY-MM-DD.json           # 记录（日志），保留 30 天
  memory-trace-index.json
```

教训和扩展文件格式：

```markdown
# 部署
> 何时读：打包、发布或安装程序前

- 打包前先退出运行中的宠物 — 文件占用会让构建失败
```

注入的核心部分 = `CORE.md`（≤2000 字符）+ 程序索引（≤1000 字符），合计不超过 3000 字符。索引放不下时按“扩展 → 新格式教训 → 旧教训标题”的顺序截取，并写明还有多少个文件未列出、用 `memory_search` 查找，不静默丢弃。日记不进索引明细，只有一行固定指引。

### 3.2 写入

| 工具 | 写入位置 | 操作 |
| --- | --- | --- |
| `memory_remember` | `CORE.md` | `add` / `replace` / `remove`；`replace`、`remove` 用 `old_text` 唯一定位条目 |
| `memory_lesson` | `lessons/<topic>.md` | 同上；新主题必须填写 `when` |
| `memory_topic` | `topics/<topic>.md` | 同上；新主题必须填写 `when` |
| `memory_diary` | `daily/` | 只追加，同日相同正文去重（不变） |

- 核心超过 2000 字符时拒绝写入，错误中给出当前用量和处理办法；缩小体积的写入总是允许，旧版超限的核心可以逐步整理。控制器手动保存同样遵守此规则。取消 v0.2 的模型自动精炼。
- 偏好变化用 `replace` 原地改写，不追加矛盾条目。`old_text` 匹配不到或匹配多条时报错，不猜测。
- `add` 前先做确定性查重（规范化后完全相同则不写入）。文件已有条目时再请 `memory.judge` 判断新条目与已有条目的关系：重复或更新/推翻某条时**不写入**，把那条原文返回给模型，由模型决定用 `replace` 改写，或传 `force: true` 确认新增。判断不可用时照常写入并在结果和状态中说明。
- 写入后由代码重新读取文件确认内容，工具结果中的 `written`、条目数和字符数来自实际文件，不依赖模型的回复。
- 教训工具说明中明确不记录：缺依赖、未配置凭据等环境问题；“某工具不能用”之类的否定结论；重试即可的瞬时错误；没有试成功的做法。这些内容会固化成以后拒绝做事的理由。

### 3.3 注入与缓存

会话第一次请求时冻结记忆快照，之后模型自己写入记忆不改变系统前缀，避免每次写入都打破提示词缓存；本会话的新写入以工具结果为准，注入说明中告知模型这一点。以下时机刷新快照：

1. 新建会话、程序重启（切回本次运行中用过的会话时沿用它的快照）；
2. 会话压缩时（压缩本来就要重建前缀，`context.compaction` 用刷新后的前缀重新计数）；
3. 用户在控制器中修改记忆（`memory.changed` 事件，`source: "user"`）。

主动问候仍读取实时记忆；飞书私聊按通道冻结，规则与桌面会话相同。

### 3.4 `memory.judge` 能力

```ts
interface JudgeQuestion { id: string; kind: string; prompt: string; options: string[] }
interface JudgeAnswer { id: string; choice: number | null }
"memory.judge": {
  ask(questions: JudgeQuestion[], signal?: AbortSignal): Promise<{ backend: string; answers: JudgeAnswer[] }>;
  status(): { backend: string; available: boolean; retryAt?: number; lastError?: string };
}
```

- 第一步实现为 `familiar.memory-judge`（`backend: "main-model"`），使用当前模型设置，一次请求可回答多题；关闭或降低思考，30 秒超时，不提供工具。
- 模型输出按不可信输入处理：必须是 JSON，题目 ID、选项序号逐项校验，无法判断时为 `null`。
- 连续失败按 60 秒、5 分钟、15 分钟冷却，冷却中直接报不可用，不每次重试。用户取消不计为后端故障。
- 题目内容是已经脱敏的记忆条目，发送给用户已配置的同一个模型服务。

### 3.5 记录

`memory-files`、`memory-judge`、`tools-basic` 与 `conversation` 发出 `memory.trace` 事件（`v: 1`），`familiar.memory-trace` 插件写入 `data/memory-trace-日期.json`，保留 30 天，每天最多 2000 条，超出只计数。记录类型：

| 类型 | 内容 |
| --- | --- |
| `write` | 层、文件、操作、是否写入、判断后端与结论、字符数 |
| `judge` | 后端、题目、选项、答案或错误、耗时 |
| `recall` | `memory_search` 的查询与命中文件，`memory_read` 读取的文件与偏移 |
| `inject` | 会话、注入的记忆字符数、本轮是否刷新快照 |

记录是诊断数据，与记忆分开存放（宪法第 77、79 条），不显示在气泡中，删除记忆不会自动删除记录。

### 3.6 本步不做

- 压缩时顺带写日记：用户决定不做，日记仍只由模型主动调用 `memory_diary`。
- 向量检索、自动把日记晋升为教训、跨文件查重：属于第二步。
- 自动迁移旧教训：旧的时间戳文件原样保留，索引中按标题列出。

## 5. 候选设计（未实现）

### 5.1 第二步：向量模型

- 只替换候选挑选：召回时按语义找相关条目，查重时跨文件找最相似的几条交给 `memory.judge`。判断与改写仍由第一步的流程完成。
- 向量按条目计算（教训一条一个、日记一段一个），不按文件计算。索引中保存模型名与维度，换模型必须全部重算，不混用。
- 向量模型固定选一个，不进入回退链；选中文可靠、在 CPU 上也能运行的多语言模型，例如 bge-m3（待实测）。路径、错误码等精确标识仍用关键词检索，与向量结果合并。
- 每轮可选：把用户消息与各文件“何时读”比对，强命中时在本轮末尾附一行文件名提示（不附正文），不调用生成模型、不改系统前缀。阈值需用第一步日志校准。
- 作为新插件与新能力实现，不改 `memory-files` 的文件格式。

### 5.2 第三步：判断模型

- Jev 作为 `memory.judge` 的另一实现；Laya 等开源模型在有足够人工修正数据后再评估。默认回退顺序待定：本地判断模型 → 云端判断模型 → 主模型。
- 云端判断模型需要用户单独提供密钥并明确同意记忆内容发给该服务，默认关闭；主模型与本地向量模型的组合是默认形态。
- 接入前先用第一步记录中的判断题离线回放，比较一致率；中文效果以实测为准。
- 每次判断记录后端，结论不一致时可抽查重做。

## 6. 风险

- 便宜模型更容易“说已保存但没调用工具”。写入结果以代码确认为准；发布结论前用更强的模型复测。
- 冻结快照意味着本会话中新写的规则只存在于工具结果里；会话很长且多次写入时，以压缩时的刷新为准。
- 主模型查重在每次新增条目时多一次小请求；写入很少时成本可控，记录中可以统计实际次数。
- 2000 + 1000 的分配是初始值，按实际记录调整时需同步本文与界面。
