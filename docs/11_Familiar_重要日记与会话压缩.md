# 重要日记与会话压缩

## 用法

模型设置中的上下文窗口留空表示默认上限 **256000 token（256K）**，可手动填写；已有手填值保持不变。有效窗口取应用上限与模型报告窗口的较小值。模型未报告窗口时暂用 32768，确认实际支持的窗口后可手填；不会把默认 256K 冒充所有模型的能力。llama.cpp 使用已分配的运行窗口。

自动压缩阈值默认 **80%**，可设置 10—95%，随供应商配置档案保存。触发前预留工具、输出和安全余量；原生计数不可用时保守估算，界面会标明。调低阈值会增加整理频率和额外模型用量，不一定更省钱。256K 是产品默认值，不是所有模型注意力或成本的最佳点。

“历史会话”仍显示完整对话，压缩后可展开该会话的交接摘要。压缩只切换后台上下文版本，不新建用户可见会话，不重置权限。“模型连接”显示压缩次数与触发量。飞书使用相同服务，保持私聊隔离；其归档仍不并入桌面历史列表。

日记由模型选择重要经历后调用 `memory_diary` 写入，按本地日期追加，每篇不超过 4000 字符，同日完全相同正文去重。也可以直接要求“把今天这件事写进日记”。闲聊和主动问候不再自动复制到日记。长期偏好使用 `memory_remember`，教训使用 `memory_lesson`。已有日记和用户编辑的身份/Skill 文件保持原样，不自动清理或重新总结。

## 四层资料

| 层 | 内容 | 使用方式 |
| --- | --- | --- |
| 完整会话 | 用户正文、助手回复、工具轨迹 | 历史管理保留，作为恢复依据 |
| 会话摘要 | 目标、约束、更正、事实、决定、完成/未完成事项、疑问、准确路径参数 | 当前会话持续携带，压缩时增量合并 |
| 近期原文 | 最近两轮完整对话和当前输入 | 尽量保留，小窗口时按整轮减少 |
| 记忆与日记 | 长期约定、重要经历、复盘教训 | 核心稳定注入，日记按需检索 |

摘要是有损整理。可靠性依靠原文可回查、近期原文和明确交接状态共同保障，不能承诺绝不遗漏。不能把日记当成任务状态，也不应在每次换窗口时强制写日记。完整会话本来就应保存，停止自动写日记不会取消历史管理。

## 算法与持久化

1. `llm.management.plan` 决定有效窗口 `W`，扣除最大输出和安全余量得到输入预算 `B`。工具预留为 `T`，触发量为 `min(B - T, floor(W × percent / 100) - T)`。
2. 每次用户发送前检查系统提示、旧摘要、历史、当前输入的计数。未触发时保持原前缀和缓存键。触发后保留最近完整轮次，尾部目标约为触发量的 55%，不足时按整轮减少，但保留当前输入。
3. 当前配置的模型合并上次摘要与新增历史，输出八个数组字段：`goals / constraints / facts / decisions / progress / pending / uncertainties / artifacts`。该调用没有工具，不执行历史中的命令。只提供可见正文和工具记录，不提供供应商私有推理块。
4. 太长的历史分块整理，每块先计数，确保压缩请求本身能装入模型。每块记录来源偏移和前一索引；上一份摘要传入下一块。
5. 校验字段和实际用量，要求结果变短并降至触发量以下。坏格式、断流、失败、超时或取消不推进会话起点，不降级为静默丢弃旧轮次。
6. 摘要和来源先落盘，再保存会话新起点并递增后台前缀版本。新请求包含固定人格/核心记忆、摘要、近期原文和新输入。
7. 模型可通过 `context_read(checkpoint, offset?, query?)` 分页定位原文，再沿返回的 `previous` 查询更早资料。

```text
data/
  conversation-session-<会话ID>.json   # 完整历史和交接指针
  channel-<通道散列>.json             # 独立私聊历史
  context-index-<会话散列>.json        # 该会话的压缩归档索引
  context-<会话散列>-<UUID>.json       # 摘要、来源片段、前一索引
home/memory/
  CORE.md
  lessons/
  daily/YYYY/MM/YYYY-MM-DD.md         # 主动挑选的重要日记
```

删除桌面会话同时清空其压缩归档内容；独立记忆不变。新建会话会保留原会话。取消产生的未激活文件不用于后续请求，仍登记在索引中以便删除。旧版只有裁剪起点而没有交接摘要时，从保存的完整历史重新整理。

缓存依赖相同输入前缀，保持 HTTP 请求头不保证命中。一次压缩会改变旧前缀，之后新上下文继续稳定追加；应观察供应商实际缓存读写用量，而不是承诺节省某个百分比。

整理请求独立预留输出预算，按模型声明优先关闭思考或采用低强度，不修改用户平时聊天的思考设置。兼容服务以 400 拒绝参数时仅回退一次到自动，后续分块沿用；鉴权、网络失败及坏摘要不自动反复重试。

## Codex 参考与差别

核对日期：2026-09-20。[Codex 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)公开区分 `model_context_window` 与 `model_auto_compact_token_limit`。窗口和自动整理阈值分别设置，不能把某个模型的默认值当成通用常数。

[OpenAI Compaction](https://developers.openai.com/api/docs/guides/compaction)公开了 Responses 自动压缩和独立压缩接口，可返回不供人阅读的加密压缩状态。这与让任意模型写文本摘要不同；公开接口也不足以证明本项目复制了 Codex 内部实现。

本版是跨供应商结构化文本交接，没有调用 OpenAI 专用压缩端点。后续可在供应商插件增加原生压缩能力，并保留可读摘要用于跨供应商切换，不能把一家供应商的加密状态交给另一家。

## 开发入口与边界

- `packages/contracts/context.ts`：交接状态和服务契约。
- `plugins/context-compaction`：触发、分块总结、原文索引、查询工具及删除归档。
- `plugins/conversation`、`plugins/channel-chat`：持久会话与后台版本。
- `plugins/memory-files`、`plugins/tools-basic`：主动日记，删除了逐轮 `record`。
- 控制器 `model-settings.js`、`experience-settings.js`：阈值、用量与摘要查看。

本版在新一轮用户发送前整理。Agent 不限制工具往返轮数或单批工具数量，每次请求仍检查输入预算，异常大的单次结果可能中断该轮。后续优先增加“工具结果完整落盘，只注入摘要和读取句柄”、安全工具轮次边界上的工作状态交接，再支持轮中压缩。

进一步改进应以固定样例验证：用户否定约束和来源锚点、更正关系、预算与日期、已做与未做的区别、连续多次压缩的摘要漂移；必要时按原文重建。不要为每轮聊天额外调用一次总结模型。

## 验证方法

`npm test`、`npm run typecheck`、`npm run build`；`node scripts/context-smoke.mjs` 在隔离 Electron 目录检查阈值保存、摘要展示、历史原文保留和无自动日记。取得保存连接使用授权后，可运行 `node scripts/context-smoke.mjs --saved-api`，仅复制配置和密文，使用合成旧历史，不复制用户聊天。

夹具验证控制流程；真实模型样例也不能代替七种供应商和连续长任务的质量评估。具体结果见 [本地验收记录](05_Familiar_本地预览验收记录_v0.1.md)。
